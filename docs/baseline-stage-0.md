## Среда и восстановление запуска

- Исходная среда: macOS arm64, Node.js 25.6.0, npm 11.8.0; workflows использовали Node.js 20.
- Согласованная среда: Node.js **22.23.2**, npm **10.9.8**. `.nvmrc` содержит точную
  версию Node.js; все четыре workflow читают её через `node-version-file`.
  `package.json` и корневая запись lockfile содержат согласованные engines.
- Для проверки использован официальный darwin-arm64 архив Node.js, проверенный по
  `SHASUMS256.txt`. Системный Node.js и настройки shell пользователя не изменялись.
- `npm ci` в отдельной временной копии успешно установил **495 пакетов**, включая
  Cypress 13.17.0. TypeScript 5.9.3, Cucumber 10.9.0.
- После диагностики выполнен `npm ci --offline` в рабочей папке из того же полного
  npm-кеша: **495 пакетов за 4 секунды**, exit 0. Версии зависимостей в lockfile
  не обновлялись. Typecheck после переустановки занял меньше секунды.

**Причина прежних задержек:** в существовавшем `node_modules` часть файлов имела
флаги macOS `compressed,dataless`. Синхронная трассировка чтения TypeScript остановилась
на `node_modules/type-fest/source/async-return-type.d.ts`; `ls -lO` подтвердил флаг
`dataless`. Отдельное чтение файла затем заняло 2.162 секунды. Это ожидание получения
содержимого выгруженных файлов, а не доказанное зависание проверки типов.
Проблема повторялась на старой установке с Node.js 25 и 22 и исчезла после `npm ci`.
Конкретный сервис, выгрузивший файлы, не установлен; настройки синхронизации не менялись.

Если проблема повторится, проверить `ls -lO` для зависимостей и восстановить их через
`npm ci`. Держать рабочую копию локально доступной; не считать старый `node_modules`
воспроизводимой установкой.

При первоначальном запуске песочница блокировала DNS npm (`ENOTFOUND`) и открытие
порта (`EPERM`). После разрешённых запусков вне песочницы установка и API-проверки
завершились. Это ограничения среды исполнения, не ошибки тестового приложения.

## Как воспроизвести

Из корня проекта:

```bash
nvm install
nvm use
node --version
npm --version
npm ci
npx --no-install tsc --noEmit
npx --no-install cucumber-js --profile default --dry-run --format summary
npx --no-install cucumber-js --profile acceptance --dry-run --format summary
npx --no-install cucumber-js --profile smoke --dry-run --format summary
npx --no-install cucumber-js --profile regression --dry-run --format summary
```

Для реальных API-тестов использовался отдельный порт 13002. В первом терминале:

```bash
MOCK_PORT=13002 npm run mock:start
```

Во втором терминале дождаться успешного health-check, затем выполнить один набор:

```bash
curl --fail http://localhost:13002/health
API_URL=http://localhost:13002 npx --no-install cucumber-js \
  --profile api-acceptance --format summary \
  --format json:reports/baseline-api-acceptance.json \
  --format-options '{"resultsDir":"reports/allure-stage0-final/api-acceptance"}'
```

Повторить с `api-smoke` и `api-regression`, заменяя также имена выходных файлов.
Перед каждым набором остановить свой mock через Ctrl+C и запустить заново:
состояние хранится в памяти. Все серверы, запущенные при сборе baseline, остановлены.
Для новой серии запусков выбрать новые каталоги результатов, чтобы не смешивать Allure.

Стандартные `npm run test:api:*` также доступны, но жёстко задают порт 3001.
Приведённые команды напрямую используют те же Cucumber-профили, меняя только порт
и формат/каталог отчёта. API-тесты не требуют запуска браузера и внешнего Booking.com.
