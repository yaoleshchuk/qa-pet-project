## Существенные замечания и исправления

1. `scripts/validate-generated-draft.js:20`: ранее проверялся только непустой отбор. Файл с одним размеченным сценарием и вторым без обязательных тегов проходил, хотя второй мог содержать undefined-шаг. В чистой копии контрольный файл с таким сценарием дал exit 0 и сообщение об успехе при одном выбранном из двух. Теперь сравнивается количество всех Gherkin pickles и выбранных сценариев, также отклоняются отсутствующие статусы. `npm run test:ai-generator` включает эту поломку и завершился exit 0; проверка по-прежнему dry-run, шаги не выполняются.
2. `tests/automation/e2e/playwright/steps/steps.ts:136` и `tests/automation/e2e/cypress/steps/steps.js:85`: валюта проверялась только по символу и коду. UI, показывающий прежнюю или неверную сумму с новым символом, мог пройти. Добавлены ожидаемые суммы двух London seed-отелей для EUR/USD/GBP. В контрольной копии удвоение отображаемой цены привело к exit 1 Playwright UI; контрольная поломка удалена.
3. `tests/automation/e2e/playwright/steps/steps.ts:164` и `tests/automation/e2e/cypress/steps/steps.js:99`: проверка карточек зависела от текущего состояния контролов и могла не проверить требуемый фильтр, если тот сбросился. Оба раннера теперь сохраняют запрошенные фильтры и сверяют с контролами, прежде чем проверять карточки. Одиночный и комбинированный сценарии выполнены обоими раннерами. Первая версия исправления ошибочно требовала все три фильтра в одиночном сценарии; оба прогона показали ошибку, после исправления выполнены повторно.
4. `.github/workflows/api-mock-tests.yml:85`: прямой Cucumber мог вернуть exit 0 при пустом отборе одного API-профиля, а результаты других профилей могли удовлетворить общей проверке Allure. Воспроизведение: `cucumber-js --profile api-acceptance --tags '@NoSuchStage9Tag'` вернул 0 при нуле сценариев. Workflow теперь использует `scripts/run-api-suite.js`, который требует непустой текущий JSON, passed-статусы и результаты Allure, и копирует диагностику каждого набора отдельно. С тем же пустым отбором wrapper вернул exit 1. Проверка фактического исполнения workflow относится к CI PR.
5. `README.md:207,295`: формулировка о всех endpoints Booking.com и прямой запуск отдельных cURL-скриптов вводили в заблуждение: сервер реализует учебный контракт, а скрипты требуют маркер выделенного runner. Текст и команда матрицы исправлены.

## Границы и дальнейшие задачи

`@WIP` исключён из обычных наборов; strict dry-run не является выполнением API/UI. Несколько неподдерживаемых UI-моделей и booking/payment/cancellation, guest capacity, ownership и постоянная авторизация не входят в учебную модель. SQL-файлы — примеры без DB harness. Внешний Anthropic API намеренно не вызывался; mock-генерация не подтверждает работу провайдера. Данный обзор не является аудитом безопасности и зелёный CI не гарантирует безопасность проекта.

Остаточная задача: отдельно провести dependency audit и согласовать major-миграцию test toolchain согласно backlog плана. Отдельно усилить сравнение идентичностей UI-сценариев и проверить диагностику/cleanup при отказах browser setup и сервера. Проверка готовности workflow по общему порту не доказывает принадлежность процесса при уже занятом порту; на локальной машине следует использовать выделенный порт и не подключаться к чужому серверу. Исторические evidence и внешний Pages-отчёт не являются доказательством актуального head.
