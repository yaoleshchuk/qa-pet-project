# План улучшения QA-проекта

Согласован 2026-09-22. Основная цель: достоверные, воспроизводимые результаты
тестирования и понятные границы учебного покрытия.

## Порядок работы

Один этап — одна задача Codex, одна самостоятельная ветка/PR. Исправления по
ревью продолжаются в задаче этапа. Следующий зависимый этап начинается после
интеграции предыдущего. Большой этап можно разделить на несколько связанных PR.
Общий чат используется для координации; этот документ и код — контекст для
следующих задач. Независимую параллельную работу выполнять в разных worktree.

Не отключать проверки и не ослаблять assertions ради зелёного результата.
Фиксировать реальные результаты, включая undefined/skipped и невозможность запуска.
Модели ниже — рекомендации на дату согласования, а не обязательная конфигурация.

## Этап 0. Воспроизводимая исходная картина

- Проверить среду и исследовать ранее наблюдавшееся зависание команд.
- Согласовать и зафиксировать Node.js локально и в CI.
- Проверить чистую установку `npm ci`, TypeScript, dry-run и реальные API-наборы.
- Зафиксировать passed/failed/undefined/skipped, команды, версии и ограничения.
- Сохранить этот план и короткий `AGENTS.md`.

**Готово:** команды воспроизводятся или завершаются понятной диагностикой;
исходные ошибки перечислены. Полностью зелёный набор на этом этапе не требуется.
Доказательства: [baseline-stage-0.md](baseline-stage-0.md).

Исторический результат на commit `6272e8a`: среда закреплена на Node.js 22.23.2 / npm 10.9.8; `npm ci` и typecheck
успешны. Старые зависимости содержали выгруженные macOS `dataless` файлы;
переустановка устранила задержки компиляции. Полный dry-run: 42 undefined / 61 skipped.
Реальные API: Acceptance 14 passed; Smoke 6 passed / 3 undefined; Regression
4 passed / 15 undefined. Результаты воспроизведены в чистой копии и рабочей папке.
Этапы 1–9 не выполнялись; в workflows изменена только настройка версии Node.js.

## Этап 1. Честный CI

- Добавить проверки на `pull_request`, использовать `npm ci`.
- Разделить в названиях и командах dry-run и реальное выполнение.
- Добавить строгую проверку отсутствующих шагов: baseline показал exit 0 у dry-run
  Cucumber 10.9.0 даже при undefined.
- Убрать подавление падений либо добавить итоговый gate по результатам всех наборов.
- Сохранять отчёты при неуспехе; завершать ожидание mock-сервера ошибкой по таймауту.
- Отделить публикацию Pages от проверок PR.
- Добавить typecheck в CI, включая скрипт генератора.

**Готово:** намеренно сломанный тест делает gate красным; отчёт доступен и после
падения. Контрольная поломка удалена. Известные ошибки следующих этапов не скрываются.

Результат: существующий JS-validator дополнен структурной проверкой JSON и возвращает
exit 1 при `undefined`/`ambiguous`; все CI-установки используют `npm ci`, а PR запускает
отдельные typecheck, dry-run и реальные API-проверки. API-наборы выполняются с
перезапуском mock, явным таймаутом readiness, итоговым ненулевым статусом и без потери
JSON/Allure/log-артефактов. Pages не публикуется из PR. Typecheck включает
`scripts/**/*.ts`.

Исторические результаты первоначальной реализации сохранены в
[stage-1-ci.md](stage-1-ci.md). Повторная интеграционная проверка относительно
актуального `origin/main` (`9c88759`) описана отдельно в
[stage-1-integration.md](stage-1-integration.md). Зелёный strict dry-run относится
только к включённому покрытию: 31 развёрнутый сценарий и 163 шага под `@WIP`
исключены и не считаются исправленными.

## Этап 2. API-контракт и mock

- Описать запросы, ответы и ошибки, например в OpenAPI; согласовать 400/422.
- Определить правила рейтинга, комментария, ID и повторного DELETE.
- Применять валидацию при POST и PUT; проверять существование отеля и принадлежность отзыва.
- Реализовать проверку дат и простую модель доступности.
- Пересчитывать цены по фиксированным тестовым курсам валют.
- Предусмотреть восстановление исходных тестовых данных.
- Добавить позитивные и негативные проверки контракта.

**Готово:** сервер и спецификации согласованы; даты и валюта действительно меняют
результат. Реализуется документированная учебная модель, а не весь Booking.com.

## Этап 3. Playwright API

- Перенести request, response и ID сущностей в типизированный Cucumber World.
- Убрать глобальное состояние; использовать один baseURL и относительные пути.
- Добавить отсутствующие шаги; согласовать формулировки и статусы с контрактом.
- Проверять статус, структуру, значения и непустые результаты позитивных сценариев.
- Самостоятельно создавать предусловия wishlist; очищать созданные отзывы.
- Проверять UPDATE отдельным GET, DELETE — отсутствием записи.
- Проверить сценарии отдельно и в изменённом порядке.

**Готово:** все принятые API-сценарии выполняются без undefined и зависимости от порядка.

## Этап 4. Cypress API

- Исправить matching Gherkin и выражений шагов.
- Проверять текущий ответ вместо фиксированного `@loginResponse`.
- Добавить недостающие CRUD- и негативные шаги.
- Настроить отдельный API-запуск против локального mock.
- Явно определить общий исполняемый набор для Cypress и Playwright.

**Готово:** заявленный общий набор проходит в обоих инструментах; контрольную ошибку
ответа обнаруживают оба. Не заявлять неподдерживаемое покрытие.

## Этап 5. Локальный UI-стенд

- Создать минимальные страницы поиска, результатов, входа и избранного поверх API.
- Поддержать даты, гостей, фильтры, сортировку и валюту.
- Реализовать язык и форму в объёме существующих сценариев.
- Использовать доступные имена элементов и устойчивые `data-testid`.
- Добавить запуск стенда и проверку готовности.

**Готово:** основные сценарии вручную воспроизводятся локально с исходными данными.
Внешний сайт допускается только как отдельный необязательный набор.

## Этап 6. UI-автоматизация

- Создавать Page Object после страницы; разделить браузерные и API-fixtures.
- Реализовать даты, гостей и фактическую отправку формы входа с проверкой результата.
- Проверять каждую карточку, все выбранные фильтры и числовую сортировку цен.
- Убрать жёсткие внешние URL; использовать относительные даты или фиксированное время
  там, где проверяются границы дат.
- Добавить реальные команды запуска Playwright UI и эквивалентные исправления Cypress.
- Сохранять screenshots и Playwright traces при падениях.

**Готово:** основной набор проходит на локальном стенде; намеренно сломанная сортировка
или игнорирование дат приводит к падению. Доступны диагностические артефакты.

## Этап 7. AI-генератор

- Сохранять результат как черновик `@WIP`, автоматически добавлять `@API`/`@E2E`.
- Проверять Gherkin и matching шагов, передавать контракт и доступные формулировки.
- Защитить существующие файлы от перезаписи и обработать пустое имя.
- Обрабатывать ошибку API и обрезанный ответ; убрать зависимость примеров от года.
- Проверять процесс в mock-режиме и описать перевод черновика в исполняемый набор.

**Готово:** непроверенный результат не включается в рабочий набор, повторная генерация
не уничтожает файлы, ошибки понятны. Реальные API-вызовы не нужны для базовой проверки.

## Этап 8. Отчётность и документация

- В README добавить матрицу: сценарий → инструмент → исполняется / черновик / пример.
- Проверить инструкции запуска из чистого клона.
- Показывать passed/failed/undefined/skipped; не смешивать старые Allure-результаты.
- Проверить cURL на macOS/Linux, согласовать URL и корректный разбор JSON.
- Обозначить SQL учебными примерами, пока нет БД и исполняемых проверок.
- Обновить этот план фактическими результатами.

**Готово:** другой человек воспроизводит проверки по README и понимает границы покрытия.

## Этап 9. Независимое ревью

В новой задаче проверить итоговый diff и сценарии отказа: пустой ответ, сломанная
сортировка, неверная валюта, чужой отзыв, отдельный запуск сценария, артефакты падения,
установка из чистой копии и соответствие README фактическим командам.

**Готово:** существенные замечания исправлены, ограничения описаны, приложены результаты.
